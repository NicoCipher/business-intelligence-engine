# Data Model

Version: 1.0

Status: Canonical

---

# 1. Purpose

This document defines the canonical information model of BIA.

The data model describes the meaning of every primary object managed by the platform.

It intentionally does not specify database schemas, storage engines, serialization formats, or implementation details.

---

# 2. Design Goals

The data model is designed to satisfy five objectives.

1. Preserve historical evidence.

2. Separate observations from conclusions.

3. Represent market knowledge as persistent objects.

4. Enable deterministic reasoning.

5. Support future autonomous intelligence.

---

# 3. Canonical Objects

The architecture consists of five primary objects.

```
Signal

↓

Entity

↓

Relationship

↓

Problem

↓

Opportunity
```

Every persistent object belongs to exactly one category.

---

# 4. Signal

## Definition

A Signal is an immutable observation collected from an external source.

Signals describe events.

Signals never describe conclusions.

Examples include:

- a Reddit discussion
- an RSS article
- a Hacker News submission
- future public sources

Signals are append-only.

Existing Signals are never modified.

---

# 5. Entity

## Definition

An Entity represents a meaningful concept extracted from one or more Signals.

Examples include:

- technologies
- markets
- customer groups
- regulations
- business activities

Entities normalize language.

Different wording may resolve to the same Entity.

---

# 6. Relationship

## Definition

A Relationship connects two Entities.

Relationships describe knowledge.

Examples include:

- belongs_to
- affects
- competes_with
- depends_on

Relationships may evolve over time.

Their existence must always remain traceable to supporting Signals.

---

# 7. Problem

## Definition

A Problem represents persistent market pain.

Problems are the primary long-lived intelligence object within BIA.

Problems accumulate:

- evidence
- history
- recurrence
- confidence

Problems are not generated by reports.

Reports describe Problems.

---

# 8. Opportunity

## Definition

An Opportunity is a time-bound commercial assessment of a Problem, captured as a dated, immutable observation.

Each Opportunity is generated once, at detection time, and is never edited afterward.

Opportunity attributes may include:

- score
- confidence
- recommendations
- supporting evidence

An Opportunity's relevance can become stale over time. Staleness is expressed by newer Opportunities linked to the same Problem, or by the Problem's own accumulated state — never by rewriting an existing Opportunity.

Problems persist. Opportunities are the dated evidence trail that accumulates against them.

---

# 9. Identity

Each canonical object owns a stable identity.

Identity never depends upon:

- titles
- wording
- presentation

Identity depends upon the underlying concept represented by the object.

---

# 10. Historical Evolution

Every canonical object falls into exactly one of two categories: an immutable historical observation, or a mutable canonical identity.

## Immutable Historical Observations

Signals and Opportunities are dated records of something that was true at a specific point in time. Each individual record is created once and never edited. New understanding is captured by creating new records, not by rewriting old ones.

Signals

- immutable; append-only

Opportunities

- immutable; one record per detection, linked to a Problem

## Mutable Canonical Identities

Entities, Relationships, and Problems represent an ongoing concept that accumulates evidence and current state across many observations. Their identity persists even as specific fields on them legitimately change over time. This is not a violation of historical integrity, provided the observations that produced that state — Signals, Opportunities, and any dedicated history record such as Problem Memory — remain intact and reconstructable elsewhere.

Entities

- accumulate references; current relevance state may change (lifecycle); identity and extraction history remain intact

Relationships

- accumulate evidence; current relevance state may change (lifecycle); identity and extraction history remain intact

Problems

- accumulate intelligence (recurrence, evidence, history); current summary fields (for example, last observed, times seen) update as new evidence arrives; full evolution is separately preserved in Problem Memory

This distinction is fundamental: mutating a current-state field on a canonical identity is not the same as rewriting history, as long as the evidence trail that produced that state is preserved elsewhere and remains reconstructable.

---

# 11. Traceability

Every object must remain traceable.

A recommendation must be explainable by:

Opportunity

↓

Problem

↓

Relationships

↓

Entities

↓

Signals

If this chain cannot be reconstructed, the intelligence is incomplete.

---

# 12. Ownership

Each object has exactly one owner.

Signals own observations.

Entities own concepts.

Relationships own knowledge.

Problems own accumulated intelligence.

Opportunities own commercial evaluation.

Reports own nothing.

Reports only communicate.

---

# 13. Future Compatibility

Future object types may be introduced.

Examples include:

- Validation
- Prediction
- Indicator
- Company
- Product

Future additions must extend this hierarchy rather than replacing it.

---

# 14. Authority

This document defines the canonical information model of BIA.

Every database schema, migration, API, collector, report generator, intelligence engine, and future autonomous agent must preserve the semantics defined here.
